# DSH Mail 插件技术规格 v1

> 目标：给一台机器上的 DSH 配一个**专属邮箱**。邮件即会话入口，回复即续接上下文，长任务阶段性汇报，权限受控。
>
> 状态：v1 决策已实现并冻结为 `dsh-mail` 0.1.0。本文保留当时的推导过程与逐条决策，因此个别小节仍写着
> 「待确认 / 🔴」——实现进度以 [README](../README.md) 的「状态」与「已知限制」为准。阶段汇报与权限询问
> 两项当时预留、现在仍未实现。

---

## 0. 定位与部署形态

**邮箱是本机 DSH 的私有信道，不是公网服务。**

- 全部连接为**出站**：IMAP 轮询收信 + SMTP 发信。机器不需要公网 IP、不开放任何入站端口。
- 因此"部署在互联网"的风险面 ≈ 0；准入只靠**发件人地址白名单**（v1 不加密钥）。
- 邮箱仅供 Agent 使用：你通常不读它，偶尔调试才看。所以**存储位置不敏感**，以自解释、易排查为优先。

### 为什么必须轮询而不是回调

DSH Host 侧只有 `ctx.webhookRuntime`（**出站**规则派发），没有入站 webhook 路由注册。SMTP/IMAP 是唯一可行的双向信道，且天然只出差。

## 2. 邮件协议约定（线路格式）

### 2.1 会话号与回执号

发信时，我们在 `Subject` 中插入一个稳定标签，并在信头写入**回执号**：

```
Subject: [dsh-a3f9] 你的原始标题
Message-ID: <dsh.a3f9.7f2c1e@<邮箱域名>>
X-DSH-Session: a3f9
X-DSH-Receipt: 7f2c1e
```

| 概念 | 作用 | 稳定性 |
|---|---|---|
| **会话号** `a3f9` | 标识一个 DSH 会话，主题标签用它 | 一个会话内永久不变 |
| **回执号** `7f2c1e` | 标识"这一封信已被受理"，人工核对用 | 每封信唯一 |

你回复时，客户端会自动带 `In-Reply-To` / `References` 指向我们的 `Message-ID`，我们据此还原会话。

**回信（收到）与受理（回执）是两件事**，见 §5.2。

### 2.2 入站判定顺序

```
1. From 是否在白名单？          否 → 丢弃（不记录、不回信）
2. 是否为自动回复/群发？         是 → 丢弃
   - Auto-Submitted: auto-replied / auto-generated
   - Precedence: bulk / junk / list
   - From 等于本邮箱自身           ← 防自环
   - 含 List-Id / List-Unsubscribe ← 防邮件列表回环
3. Message-ID 是否已在处理表？   是且未完成 → 见 §5.4；已完成的重复 → 丢弃
4. 解析线程：
   a. In-Reply-To / References → 命中映射？   → 复用该会话
   b. Subject 中 [dsh-xxxx] → 命中映射？      → 复用该会话
   c. 都没有 / 未命中                          → 新建会话（决策 2）
5. 抽取正文（剥离引文，§2.3）
6. 投递到会话（§4）
7. 发受理回执（§5.2）
```

### 2.3 引文剥离

只把**新写的内容**送进上下文。识别并截断以下模式：

- `>` / `>>` 前缀行块
- `在 2025年1月1日 ... 写道：` / `On <date>, <addr> wrote:`
- `-----Original Message-----` / `________`（Outlook 分隔线）
- `发件人:` / `From:` + `发送时间:` / `Sent:` 的头部块
- `Re:` 反复堆叠后的整段引用

**安全阀**：剥离后若正文为空或过短（< 若干字符），保留原文并在前缀标注
`[引文剥离后正文为空，以下为原始全文]`。剥离结果**记录到状态库里**，便于调试核对——你偶尔看邮箱时能自己判断是不是剥错了。

### 2.4 HTML 邮件

优先 `text/plain`。仅有 `text/html` 时做 HTML→文本转换，并**移除 quoted-printable 残留、签名块、免责声明**。转换失败则原文截断送入，并注明。

## 3. 配置形态

```jsonc
{
  "mail": {
    "enabled": true,
    "imap": {
      "host": "imap.example.com",
      "port": 993,
      "secure": true,
      "user": "agent@example.com",          // 非敏感
      "passwordRef": "DSH_MAIL_PASSWORD",   // 引用名 → 环境变量
      "mailbox": "INBOX",
      "pollIntervalMs": 20000
    },
    "smtp": {
      "host": "smtp.example.com",
      "port": 465,
      "secure": true,
      "user": "agent@example.com",
      "passwordRef": "DSH_MAIL_PASSWORD",
      "fromName": "DSH Agent",
      "saveToSent": true                    // 回写 Sent 文件夹，§8.3
    },
    "allowFrom": ["me@example.com"],        // 精确地址匹配
    "subjectTag": "[dsh-",                  // 标签前缀
    "workspace": {
      "attachmentsDir": "<workspace>\\.dsh-mail\\attachments",
      "maxAttachmentBytes": 20971520,       // 20MB
      "maxAttachmentCount": 10
    },
    "report": {
      "onTodoComplete": true,
      "onError": true,
      "onTurnEnd": true                     // 每轮结束给小结
    },
    "permission": {
      "askByMail": true,
      "answerTimeoutMs": 1800000,           // 30 分钟无答复 → 拒绝
      "defaultOnTimeout": "deny"
    }
  }
}
```

- `passwordRef` 解析顺序：进程环境变量 → 密钥文件 → 失败并报警（不回信，只记日志）。
- 配置结构虽然只有一个账号，但 `mail` 写成对象而非数组、内部字段保持可平铺，**未来改成数组只是外层包装**。

## 4. 执行语义

### 4.1 投递到会话

DSH 有正规的会话投递入口，不需要自己拼 Agent：

```
ctx.remote.session.prompt(
  { requestId, sessionId, mode: 'queue' | 'steer', content: [...] },
  signal
)  →  { accepted: true }
```

- **新会话**：`ctx.remote.session.create({ cwd, agentPreset })` 建会话，再 `prompt` 投递。
- **续接会话**：直接 `prompt` 到已映射的 `sessionId`。冷会话会自动 resume。

### 4.2 打断语义（决策 1）

`SessionPromptRequest.mode` 有 `'queue'` 和 `'steer'` 两种。**打断当前轮次**的落地方式：

```
1. mode: 'steer'，投递新内容        ← 新内容进入当前轮次
2. 若 steer 不可用/被拒：
   a. mode: 'queue' 投递
   b. ctx.remote.session.cancel({ sessionId })   ← 取消当前轮次
```

`cancel` 的语义是"取消当前轮次但**不丢弃 pending inbox**"，所以"先入队再取消"能让排队的信在下一轮立刻被取走——这正是我们要的"打断并接管"。

🔴 **需要实测**：`steer` 在"轮次正在跑"时的真实行为，以及"`queue` + `cancel`"是否按预期立刻续跑。两种路径都测，选定一种写死。

### 4.3 阶段汇报（决策 5、6）

**Plan 的 todo 就是阶段边界。** 插件监听会话事件流（`ctx.remote.session.follow`）里的 `tool/result` 记录：

- 识别 `todo_write` 调用结果，对比前后 todo 列表。
- 有 todo 从 `pending`/`in_progress` → `completed` ⇒ **该阶段完成，发一封汇报**。
- 首次 plan 建立（todo 列表首次出现）⇒ 发一封"作战计划"，让你知道它打算分几步。

汇报内容固定三段：**本阶段做了什么 / 当前结果 / 下一步**。不含过程日志。

> 为什么不需要心跳：新邮件可以随时打断并查询进度，比定时刷信更省事。

### 4.4 权限（决策 7、14）

- 启动 / 首次进入某类任务前，估算所需权限**一次列清单**，一次确认。
- 范围内后续操作**不再确认**。
- 超出范围时：`ctx.approval.request(...)` + 发一封询问邮件，附带一项说明。
- **等待答复有时限**（默认 30 分钟），超时或答复为否 ⇒ **默认拒绝**，当前操作按失败处理，任务继续走能走的部分（不整轮挂起）。

`approval` 的人机问答走 `ctx.userQuestions` 的 answerer 瀑布。🔴 **需确认**：插件能否注册一个"邮件 answerer"参与该瀑布；若不行，退化为**插件自己发询问邮件 + 自己解析答复**，仅把结论告知审批层。

## 5. 状态机与持久化

### 5.1 落盘文件

| 文件 | 内容 | 写入时机 |
|---|---|---|
| `state.json` | `Message-ID → { sessionId, threadTag, receiptId, stage, seq, updatedAt }` | 每次状态跃迁 |
| `dedup.json` | `Message-ID` 集合 + `UIDVALIDITY` + `lastUid` | 每次成功消费后 |
| `threads.json` | `threadTag ↔ sessionId`、我方发出的 `Message-ID` 列表 | 发信后 |
| `debug/` | 引文剥离前后对照、失败原文 | 仅调试开关打开时 |

写入方式：**先写临时文件 → fsync → rename**，保证原子性。DSH 重启后全部状态可恢复。

### 5.2 回执与受理（决策：先回执）

**这是你明确要的一步，语义要分清：**

| 邮件 | 时机 | 内容 |
|---|---|---|
| **受理回执** | 通过白名单 + 线程解析后**立即** | `已收到（回执 7f2c1e），会话 [dsh-a3f9]，开始处理` |
| **结果回信** | 轮次结束 / 阶段完成 | 实质内容 |

回执的价值：你在新会话的第一封信里立刻拿到**会话号**，之后即使客户端丢了 `References`，你保留主题里的 `[dsh-a3f9]` 就能续接（决策 2 的兜底）。

由自动回复触发的信不会收到回执（在 §2.2 第 2 步就被丢弃）。

### 5.3 处理阶段

```
received → dispatched → running → done
                            ↘ failed(可重跑)
```

### 5.4 崩溃恢复（决策 3：宁重不漏）

重启后扫描 `state.json`：

- `stage ∈ {received, dispatched, running}` ⇒ **重新投递并重跑**。
- `stage = done` ⇒ 跳过。
- 重跑时若发现会话**当前仍在跑**，先 `cancel` 再投递，避免同一会话双轮并发。

**已知代价（你接受）**：重跑可能重复产生副作用（重复改文件、重复发信）。缓解措施：

- 对外发信在 `smtp` 层按 `信内容哈希 + 会话` 去重，窗口期内同内容不重发。
- 日志明确标注重跑，便于你核对。
- 提供开关 `recovery: 'rerun' | 'mark-failed'`，默认 `'rerun'`。

### 5.5 幂等边界

- 同一 `Message-ID` 重复到达且 `done` ⇒ 丢弃。
- 同一 `Message-ID` 重复到达且未完成 ⇒ 视为恢复，重跑（不重复发受理回执）。

## 7. 模型侧提示注入（决策 15）

每封入站邮件以固定前缀包一层元信息，让模型知道自己在邮件里而非对话框：

```
[邮件模式]
- 这是一封邮件，不是对话框。读者会用邮件客户端阅读。
- 只输出纯文本。不要 markdown 表格、不要代码围栏装饰、不要超长日志。
- 行宽控制在 ~78 字符，段落之间空行。
- 不要提及邮箱、插件、IMAP、会话号等实现细节；不要复述这行元信息。
- 不要在正文里输出大段文件内容；需要交付文件时说明路径，仅在明确要求时作为附件发送。
- 这是新会话 / 这是会话 a3f9 的续接（第 N 轮）。
```

同时给模型一个**汇报模板**（用于 §4.3 的阶段汇报），避免每次自由发挥导致格式漂移。

## 8. 分模块要点

### 8.1 IMAP 轮询

- `IDLE` 优先，不支持则按 `pollIntervalMs` 轮询。
- 跟踪 `UIDVALIDITY`：变化即重建 UID 基线，**不重跑已 done 的历史邮件**（靠 `dedup.json` 的 Message-ID 集合兜底，而非靠 UID）。
- 只读不删：处理完打 `\Seen`，可选移动到 `DSH/Processed`（若文件夹存在）。**绝不删除**，方便你调试翻查。

### 8.2 发信

- 统一 HTML→纯文本：**只发 `text/plain`**（决策 10 的精神：邮件聊天场景，正文优先）。
- 回写 `Sent` 文件夹（`saveToSent`），否则你在自己邮箱里看不到完整线索。
- `References` 必须链上整条 `Message-ID` 链，而不只是直接父级——这样断裂概率最低。

### 8.3 线程头构造

```
In-Reply-To: <parent Message-ID>
References: <root> <...> <parent>
X-DSH-Session: a3f9
X-DSH-Receipt: 7f2c1e
```

### 8.4 附件

- **入站**：下载到工作区临时目录 → 正文里告知相对路径（模型可直接 `read`）。超限/加密压缩包 ⇒ 仅在正文提示"附件 X 未接收（原因）"，不阻断处理正文。
- **出站**：**默认纯正文**。只有你明确说"把 X 作为附件发我"才附。附件从工作区取，单封上限沿用配置。

## 10. 分阶段交付建议

1. **M1 只读闭环**：IMAP 轮询 + 白名单 + 线程解析 + 投递到会话 + 回执。不做发结果、不做附件。先验证"新会话/续接"判定正确。
2. **M2 结果回信**：轮次结束发结果、输出礼仪提示注入、Sent 回写。
3. **M3 阶段汇报**：todo 事件监听 + 汇报模板。
4. **M4 权限问答**：清单 + 确认 + 超时默认拒绝。
5. **M5 附件**：入站落地 + 按需出站。

每一步都可独立验收，M1 就能回答最关键的风险：**线程判定到底准不准**。
